## 1. Problem

A KSSM secondary-school teacher has to produce:

- one **RPT** (Rancangan Pengajaran Tahunan) per subject each year, showing which SPs (Standard Pembelajaran) are taught in which school week, and
- one **RPH** (Rancangan Pengajaran Harian) per lesson, printed or kept as PDF.

They also need to know, at any time, how far each class is through the syllabus compared with the RPT.

Writing the plans isn't the hard part. Keeping **dates, days, times and SPs right** is, because:

- the school timetable changes several times a year;
- holidays, exams and events differ by form (an exam week for Form 4 is a normal week for Form 1);
- lessons get postponed or cancelled, and the next lesson has to pick up where the class really is.

Before this project the teacher kept one Google Sheet per subject with one tab per week, and made each new week by copying last week's tab and fixing the dates, times and SPs by hand.

## 3. Goals and non-goals

### Goals
1. **G1 — Weekly RPH in minutes.** Opening a week shows that week's RPH pages, already correct, ready to print.
2. **G2 — Reality-driven pacing.** Each lesson's SPs follow the class's actual progress. A postponed lesson's content moves to the next lesson automatically.
3. **G3 — Always know where each class stands.** Weeks ahead of or behind the RPT, % of the DSKP done, and an early warning when the remaining SPs won't fit before the syllabus end.
4. **G4 — Timetable and calendar changes cost one file.** A new timetable or takwim is a new markdown file; every future lesson updates itself, and past lessons never change.
5. **G5 — Private by design.** No personal or school data leaves the teacher's devices, except through the teacher's own Google Drive (Phase 3).
6. **G6 — Works offline, free to run.** Installable web app, hosted on GitHub Pages, with no server and no subscription.

### Non-goals
- Several teachers, sharing, a school-wide system, or panitia approval workflows.
- Reading PDFs. Inputs are hand-checked markdown; source PDFs are only for reference.
- AI inside the app. AI drafts files (difficulty ratings, later activity text) outside the app, the teacher reviews them, and the app reads only those files.
- Generating the official KPM RPT template. Any clear table is acceptable.
- A phone-first layout (it may come later).

## 4. Rules the product must keep

These come from the pipeline and app specs. They are listed here because every phase has to respect them.

| # | Rule |
|---|---|
| PR1 | The **RPT is a fixed yardstick**. It is generated once, frozen, and never regenerated by weekly planning. |
| PR2 | **RPHs follow actual progress** in DSKP order. The RPT only sets how much time each SP gets. |
| PR3 | A lesson is **Taught by default**. The teacher marks only the exceptions: Postponed or Cancelled, each with a typed reason. |
| PR4 | **Past lessons never change.** Future lessons are rebuilt on every run unless the teacher edited them (Status or Catatan). |
| PR5 | **Markdown is the source of truth.** The app's stored rekod can always be exported as the exact markdown the CLI writes, and a re-picked file wins after the teacher confirms. |
| PR6 | **Same inputs, same output.** Planning is deterministic, and the CLI and the app share one planner. |
| PR7 | **Holidays, exams and events are data**, read from the takwim and the events file each year, and applied per form. |
| PR8 | **No personal data is published.** The public `rph-mate` repo holds only app and core code. |

## 5. Features

### 5.1 Phase 0 — RPH pipeline (CLI) · Built
- **F0.1 RPT generator** (`node src/cli/rpt.js`). Spreads SPs over teaching weeks by difficulty rating (1–3), avoids holidays and exams, fits half the topics before the mid-year exam, and ends the syllabus 2 weeks before the final exam. Writes markdown and printable HTML, with a "Peruntukan SP" appendix.
- **F0.2 Weekly RPH run** (`node src/cli/rph.js --classes … --week n`). Updates each class's rekod file and writes one HTML file per subject and week, with one A4 page per lesson.
- **F0.3 Year simulation** (`node src/cli/simulate.js`). Replays the year week by week to check that an undisturbed class tracks the RPT.
- **F0.4 Ahead/behind summary** printed per class.

### 5.2 Phase 1 — Web app, weekly loop · Built, unchecked
| ID | Feature | Acceptance |
|---|---|---|
| F1.1 | **Profile**: the teacher's name, printed as NAMA GURU | Typed once on the Files screen; appears on every RPH page |
| F1.2 | **Load inputs**: pick the `sample/` and `output/` folders, or drop `.md` files | Only `.md` files are read; missing referenced files are listed; Week and Classes stay locked until none are missing |
| F1.3 | **Week view**: one card per lesson of the takwim week | Opens on today's week; ◀ ▶ and Today navigate; holidays are shown as grey day labels; exam lessons are grey cards with no buttons |
| F1.4 | **Mark lessons**: Taught / Postponed / Cancelled, attendance, notes | Postponed and Cancelled need a reason; every change re-plans the week; cards update in under 100 ms |
| F1.5 | **RPH preview and print** | Live preview of the real printable HTML; Print week; Open in new tab; a cancelled lesson has no page; a postponed lesson shows "PdP ditunda kerana: …" |
| F1.6 | **Position badges** per class in the top bar | Green on track, blue ahead, amber 1 week behind, red 2+ weeks behind |
| F1.7 | **Classes dashboard** | Per class × subject: current SP, % DSKP done, RPT week of that SP, position, RPT end week; "won't fit" warning |
| F1.8 | **Save rekod** | Downloads changed rekod files byte-for-byte as the CLI would write them; an "Unsaved changes" flag turns red after 7 days |
| F1.9 | **Re-pick check** | A re-picked rekod that differs lists the lessons that differ, side by side; the teacher chooses Replace or Keep |
| F1.10 | **Offline and installable** | A service worker caches the app; it installs as a PWA in Chrome or Edge |
| F1.11 | **Release as RPH Mate** | `node tools/release.js ../rph-mate` copies only code to the public repo and sets the production name |

### 5.3 Phase 2 — Progress · Planned
- **F2.1 History import.** Seed each class's rekod with weeks M12–M35 of 2026 from the existing Google Sheets (SK, MAT, PJPK). Needs the Sheets shared.
- **F2.2 Progress view.** Per class: % of SPs completed over time, gap to the RPT over time, list of postponed and cancelled lessons with reasons.
- **F2.3 All classes.** Add the remaining class × subject rows (1S ASK, 4H SK with tutorial, 2D/2J PJPK). PJPK runs without SPs until its DSKP is added.
- Rule: an SP is **completed** when a lesson covering it was taught (not postponed or cancelled).

### 5.4 Phase 3 — Google Drive sync · Planned
- **F3.1** Sync the app's data through one store file in the teacher's own Google Drive, so the laptop, desktop and tablet share the same rekod.
- **F3.2** Works offline; syncs when online. Conflicts are resolved last-writer-wins per record, with timestamps.
- **F3.3** Retires "one main device" and makes Save rekod optional (it stays as a backup or export).

### 5.5 Phase 4 — RPT in the app · Planned
- **F4.1** Generate the RPT from DSKP, takwim and the difficulty file inside the app, preview it, and **freeze** it as a stored snapshot.
- **F4.2** Regenerating is a deliberate action that shows what changes; weekly planning only ever reads the frozen snapshot.

### 5.6 Phase 5 — Later · Idea
- AI-drafted activity text per SP, written to a reviewable file outside the app.
- Editing inputs (class file, events, Batal days) inside the app.
- Phone layout; charts; a yearly rollover assistant (new takwim, class list, DSKP).

## 6. Non-functional requirements

| Area | Requirement |
|---|---|
| Speed | After a mark, cards, badges and dashboard update in < 100 ms for one class-week; the preview redraws afterwards without blocking clicks |
| Offline | Everything except AI drafting and (Phase 3) sync works with no network |
| Privacy | School files stay in the browser (IndexedDB) or the teacher's Drive; no analytics, no third-party scripts |
| Cost | Free: GitHub Pages, no backend, no paid APIs |
| Browsers | Current Chrome and Edge on Windows (laptop); Chrome on Android tablet for viewing |
| Correctness | Same inputs → the app's rekod text is identical to the CLI's; covered by `node test/all.js` |
| Durability | The app asks for persistent storage and warns when refused; the markdown export is always available |

## 7. Success measures
- Weekly RPH session (mark last week, print next week) takes **under 10 minutes**.
- **Zero hand fixes** to dates, days or times after a timetable change.
- An undisturbed class stays "On track" all year in the simulation (already true for 4S Matematik 2026).
- The teacher stops using the Google Sheets and the Apps Script stopgap.

## 8. Risks

| Risk | Mitigation |
|---|---|
| Browser clears IndexedDB, so unsaved marks are lost | Persistent storage request, warning banner, a red unsaved flag after 7 days, Save rekod; Drive sync in Phase 3 |
| App never checked in a real browser | Phase 1b manual checklist before real use |
| Input markdown drifts from the formats the parsers expect | Parsers fail loudly with file and line; formats are frozen in the pipeline spec |
| Personal data leaks through the public repo | Separate `rph-mate` repo; the release script copies only allowed code file types |
| Drive sync conflicts corrupt a rekod | Per-record merge with timestamps; markdown export as a backup; to be designed in Phase 3 |
